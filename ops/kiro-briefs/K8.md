# K8 — verify the hook actually triggers

**Goal:** turn a NOT VERIFIED line in the evidence file into an observation, or into an honest
negative result.

**Surface:** Kiro CLI on Windows (PowerShell). Rewritten 2026-11-10 against the current hooks docs
(<https://kiro.dev/docs/hooks/>, <https://kiro.dev/docs/hooks/types/>, page dated 2026-11-06).

## Why this matters

`KIRO_SESSION_EVIDENCE.md` says, from 2026-10-31:

> Native automatic hook discovery/trigger execution remains **NOT VERIFIED** and must be
> demonstrated during T2. A manually invoked script is not evidence of a native trigger.

`.kiro/hooks/domain-typecheck.json` declares a `PostFileSave` hook with matcher
`(^|/)src/domain/.*\.tsx?$`, running `bash .kiro/hooks/typecheck-domain.sh`, timeout 30 seconds.
The JSON parses and the regex matches the right POSIX paths. What has never been seen is Kiro
running it by itself.

This is cheap and it is the difference between "we configured a hook" and "we used one", which is
exactly what the Technological Implementation criterion asks about.

## Three things the docs change about the old brief

1. **The File Save trigger fires when the *agent* saves or modifies a file.** The docs describe it as
   triggering "when the agent saves or modifies files matching specific patterns". The old brief
   told the human to save a file in an editor. In the CLI there is no editor, so **ask the agent to
   make the edit**. A file changed by hand outside the session is not the trigger.
2. **The command probably cannot run on this machine as written.** The hook calls `bash`. The owner
   is on Windows PowerShell, where `bash` exists only if Git Bash or WSL is installed. This has
   **not been checked** — it is the first thing to find out.
3. **The matcher may not match Windows paths.** The regex requires `/`. If Kiro passes a path with
   `\` the hook silently never fires, and that would look identical to "hooks do not work". Rule
   this out before concluding anything.

Per the docs the command runs in the project root and receives the event as JSON on STDIN; a
non-zero exit shows STDERR as a warning. The script ends with `exit 0` on purpose, so a *failing*
typecheck will not show as a hook error — look for its printed `[ghostlight hook]` lines instead.

## Before the session

Run these yourself in PowerShell and write the answers down:

```powershell
Get-Command bash -ErrorAction SilentlyContinue   # is there a bash at all?
kiro-cli --version                                # must be 3.0.0 or later
kiro-cli chat --help                              # confirm the flags; the 2.x ones may have changed
```

## Paste this into Kiro

```text
I need to find out whether the PostFileSave hook in .kiro/hooks/domain-typecheck.json
actually fires by itself. Do not run .kiro/hooks/typecheck-domain.sh yourself and
do not describe a manual run as a trigger -- that is the specific thing this
experiment must not do.

Step 1 -- trigger, inside the hook's scope.
Add a single blank-line-free comment line "// k8-hook-probe" at the end of
src/domain/ids.ts using your normal file-write tool. Then say, verbatim, whether
any hook output appeared on its own (look for lines starting "[ghostlight hook]").
Do not run anything else in between.

Step 2 -- revert.
Remove that comment line again so src/domain/ids.ts is byte-for-byte what it was
(check with git diff; it must show nothing).

Step 3 -- control, outside the hook's scope.
Add the same kind of comment line to src/ui/importGuard.ts, then say verbatim
whether any hook output appeared. Revert it and confirm git diff is empty.
The hook must NOT fire for this file; if it does, the matcher is too broad.

Step 4 -- report.
State plainly one of:
  A) fired for step 1, silent for step 3  (hook works, matcher is real)
  B) did not fire for step 1              (say what you saw instead)
  C) fired for both                       (matcher too broad)
Do not claim A unless you actually saw the hook's own output.

If the result is B, diagnose before changing anything: is bash present, does the
matcher match the path form Kiro uses on Windows, is the hook listed by /hooks?
Report each answer. Only then, and only if the cause is the Windows environment,
propose this repair and wait for my yes before applying it:
  - command: "npm run typecheck"   (no bash dependency)
  - matcher: "[/\\\\]src[/\\\\]domain[/\\\\].*\\.tsx?$"
After applying an approved repair, repeat steps 1 to 3.

At the end run npm run lint, npm run typecheck, npm test and npm run build and
report the real results. Do not touch anything under src/ except the two probe
lines, and make sure both are reverted.
```

## Record either outcome

- **Fires (A):** append to `KIRO_SESSION_EVIDENCE.md` the date, which file was edited, and what the
  hook printed, verbatim. Replace the NOT VERIFIED wording.
- **Does not fire (B) or fires too much (C):** say so just as plainly, with what was tried and what
  the diagnosis found. If Kiro repaired the hook, record the before and after of
  `.kiro/hooks/domain-typecheck.json` and re-run the three steps.
- Copy the outcome into the *Agent hooks* `TO FILL` block of `docs/kiro-writeup.md`.

A negative result honestly recorded is worth more than a claim, and it is still evidence of real use.

## Acceptance

- Steps 1 and 3 each have a verbatim observation, or the exact words "no output appeared".
- `git diff` is empty for `src/` after the session.
- The outcome is one of A, B or C, supported by what was seen, not inferred.
- `npm run check` result reported with real numbers.

## Must not change

Anything under `src/` (both probes reverted), the hook's *purpose* (report-only typecheck, no
agent-prompt action, no blocking), or `tech.md`'s rule against agent-prompt hooks. A repair to the
hook's `command` and `matcher` is allowed only if the diagnosis shows the Windows environment is the
cause, and only with the owner's approval.
