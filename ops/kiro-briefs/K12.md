# K12 — variety and experimentation with Kiro's own tools

**Goal:** try the Kiro features that could genuinely help this project, and record what each one
actually changed — including the ones that did not help.

**Surface:** Kiro CLI, and optionally Kiro Web for the custom-agent check (see step 1).

## Why this matters

Technological Implementation is 20% and asks: "Was a **variety** of Kiro tools used impactfully? …
Was there **experimentation**?" The Devpost write-up also asks, tool by tool, about custom agents,
hooks, MCP and powers. Today `main` has specs, steering and one hook that has never been seen to
fire (K8). It has no custom agent, no MCP server and no power.

**The rule that governs this brief:** do not bolt a feature on for the checklist. The research plan
warned against it and a judge can tell. For each tool below the honest outcomes are *used and it
helped*, *used and it did not help*, or *considered and deliberately not used, because…*. All three
go in the write-up. Only the first two need code.

Facts below come from the current docs: custom agents
(<https://kiro.dev/docs/custom-agents/>, 2026-11-03), hooks (<https://kiro.dev/docs/hooks/>), MCP
(<https://kiro.dev/docs/mcp/>) and powers (<https://kiro.dev/docs/powers/>).

## Do K8 first

Step 2 below builds a second hook, and you should know whether the first one fires on this machine
before adding another.

## The four experiments

### 1. A custom agent: `ghostlight-reviewer`

A project agent lives in `.kiro/agents/ghostlight-reviewer.json` (or `.md`) and is shared through
version control. It replaces the old habit of leaving `--trust-tools=` empty and approving every
action by hand: CLI V3 uses `permissions.rules` instead, for example
`{ "capability": "shell", "match": ["npm run *"], "effect": "allow" }`.

Shape the agent as a **read-only reviewer**: it may read files and run `npm run lint`, `npm run
typecheck`, `npm test` and `npm run build`; it may not write source, install packages or push. Give it
the steering and requirements as `resources` (`file://` entries). The point is a reviewer that can
verify the Kiro-authored code without being able to change it, which also reinforces the project's
provenance rule.

Optional: the docs say Kiro Web loads project agents committed under `.kiro/agents/` and can invoke
them for sub-agent delegation (you cannot select one as the primary Web session agent). If you
have Web access, check it loads there and record the difference from the CLI.

### 2. A second, lighter hook

Add one more `.kiro/hooks/*.json`: a **`Stop`** hook (the agent finished its turn) or a
**`SessionStart`** hook, running a deterministic **command**, for example a script that prints
`git status --short` and the last `npm run lint` outcome, so every turn ends with a visible health
line. The hook doc lists these triggers as available in CLI V3.

**No agent-prompt hook.** `.kiro/steering/tech.md` forbids them because a prompt hook can spend
quota in a loop. Keep it report-only (exit 0) and quick (set `timeout`). Because the owner is on
Windows, do **not** depend on `bash`; use `npm run …` or a small `.mjs` script run by `node`.

### 3. An MCP server that earns its place: Playwright

`.kiro/settings/mcp.json` (the workspace file, so it travels with the repository) can declare a
server in `mcpServers`. The most useful one here is a **Playwright MCP server**, so Kiro can open the
built app, take screenshots and check keyboard focus and reduced motion itself, which is exactly the
loop K10 needs and the reviewer harness only does after the fact. Kiro must look up the current
official package name and an exact version, pin it, and not guess either.

If the server needs a browser download, an account or a key, or cannot connect on this machine,
that is a result; record it and stop. Keep any secret out of the file (`env` references, not values)
and out of Git. Check `kiro-cli` shows the server connected before relying on it.

### 4. A power — decide, do not assume

A power is a directory with `plugin.json` (the manifest, including keywords that activate it),
optional `skills/<name>/SKILL.md` and an optional `mcp.json`. The docs distinguish it from steering
(Kiro-specific context), from skills (portable instruction packages) and from MCP.

The one candidate worth considering is a small **`ghostlight-invariants` power** whose skill states
the six operations and the "authored requirement is never filled from computed state" rule, so a
future session loads them on the keywords `prop`, `cue`, `replay`. But `.kiro/steering/tech.md`
already carries those invariants and is loaded automatically. If a power would only duplicate
steering, **say so and do not build it** — "considered, not used, because steering already covers
it" is a legitimate, honest answer. Build it only if you can name something it does that steering
does not.

## Paste this into Kiro

```text
Experiment with Kiro's own tooling for Ghostlight, and record honestly what each
experiment changed. Do these in order and stop to report after each one. Do NOT
touch src/, tests/ or package.json in this task. Everything new goes under .kiro/,
and nothing under .kiro/ may be added to .gitignore.

1. Custom agent. Create .kiro/agents/ghostlight-reviewer.json: a read-only
   reviewer. Allow reading files, and shell commands matching "npm run lint",
   "npm run typecheck", "npm test", "npm run build" only. Deny writing source,
   installing packages and git push. Include .kiro/steering/*.md and
   .kiro/specs/ghostlight/requirements.md as file:// resources. Start a session
   with it, ask it to run the four checks and summarise, and confirm that a
   write attempt is refused or prompts. Report exactly what happened, including
   any permission-rule syntax you had to correct against the docs.

2. Second hook. Add a Stop (or SessionStart) COMMAND hook, report-only, exit 0,
   with a timeout, no bash dependency (Windows PowerShell host). It should print
   one health line, e.g. git status --short and whether lint passes. No
   agent-prompt action. Say whether it fired by itself and what it printed,
   verbatim -- if it did not fire, say that.

3. MCP. Look up the current official Playwright MCP server, pin an exact version,
   and add it to .kiro/settings/mcp.json. Confirm it connects. Use it once to
   open the production build (npm run build, npm run preview), take a screenshot
   of the Stage view, and report the result. If it cannot connect or needs
   anything I have not approved, stop and tell me; do not work around it.

4. Power. Tell me whether a ghostlight-invariants power would do anything that
   .kiro/steering/tech.md does not. If yes, name it, then build it as plugin.json
   + skills/. If no, say so and do not build it.

Finish with a table: tool, what it changed, whether it helped, what failed,
verbatim evidence. Then run npm run lint, npm run typecheck, npm test and npm
run build and report the real numbers.
```

## Record

For each experiment, in `KIRO_SESSION_EVIDENCE.md`: the exact config written, what happened,
verbatim, and what failed. Then fill the matching blocks of `docs/kiro-writeup.md` — *Custom agents*,
*Agent hooks*, *MCP*, *Kiro powers* — with the real outcome. A "considered and not used, because"
answer fills a block as legitimately as a "used" one. Never describe a tool as used if it was not.

## Acceptance

- Each of the four experiments has a verbatim observation or a stated reason for not being built.
- New files are only under `.kiro/`, are tracked by Git, and `.gitignore` does not mention `.kiro`.
- The agent's permission rules are the narrow ones above, not allow-all; the hook has no agent-prompt
  action; no secret or token is written to any file.
- `git diff --stat` shows no change under `src/`, `tests/` or `package.json`.
- `npm run check` green with the real numbers.

## Must not change

`src/**`, `tests/**`, `package.json`, `tech.md`'s no-agent-prompt-hooks rule, or the existing
`domain-typecheck.json` hook (K8 owns that one).
