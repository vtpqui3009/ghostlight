# K7 — the empty state and the first screen

**Goal:** make the first screen a judge sees explain the tool and its limits without being asked.

**Surface:** Kiro CLI. Run it right after K3, which touches the neighbouring stage region.

K2 is **already done** (2026-11-10, reviewer): the empty state now sits inside the single `<main>`
landmark in `src/App.tsx`, and the axe baseline is empty. Keep it that way — the first screen is
scanned by `tests/e2e/specs/accessibility.spec.mjs`.

## What already exists

`src/App.tsx` (the block under `{!scenario && !loadError && (` inside `<main>`) renders
`<h2>No Scene Loaded</h2>` with "Load a demo or start with an empty scene" and seven buttons — six
demo scenes and an empty one, built from `DEMO_SCENARIOS`. The honesty subtitle
"Planned state checker — not live tracking" is in the header and is covered by a smoke test.

That is thin for a first impression, and "No Scene Loaded" tells the reader what the program lacks
rather than what they can do.

## Paste this into Kiro

```text
Rewrite Ghostlight's empty state in src/App.tsx so the first screen explains
itself. Keep all seven existing choices working.

- Say in one or two sentences what the tool does: it replays a prop plan in cue
  order and reports where the plan contradicts itself.
- Keep the honesty limit visible without it being a wall of text: this is the
  planned state, not live tracking; it never sees the real stage; the bundled
  scenes are invented.
- Give the demo buttons a sentence each, or group them, so a newcomer knows that
  "Valid Control" is the one that should report nothing and "Missing Handoff" is
  the one that fails. Right now they are seven bare names.
- Suggest one obvious first move rather than presenting seven equal options.

Keep it short. Do not add a tour, a modal, a splash screen or an animation, and
do not hide controls for effect.

Then run npm run lint, npm run typecheck, npm test and npm run build and report
the real results.
```
