# K11 — property-based testing, through Kiro

**Goal:** implement the property-based tests that `.kiro/specs/ghostlight/tasks.md` already
specifies and that were never written, and report honestly whether they found anything the 235
example-based tests had missed.

## This is not new scope — it is an unfinished Kiro task

`.kiro/specs/ghostlight/tasks.md`, section **2.6 Property-based tests**, says:

> - Add `tests/pbt/*.test.ts` with fast-check: single custody, terminal consumption,
>   new-instance replenishment, deterministic ordering, immutable rejection, causal ordering,
>   own-key-safe dictionaries.
> - Record seed and minimized counterexamples; make them reproducible.
> - Acceptance: each property holds or reports a reproducible counterexample; determinism holds
>   across repeated runs; input is never mutated or frozen by the engine.

`.kiro/specs/ghostlight/design.md` line 235 lists the same six properties. Verified on 2026-11-10:
`tests/pbt/` **does not exist** and `fast-check` is **not in `package.json`**. So the specification
committed to this and the implementation stopped at 2.5. Kiro wrote the spec; Kiro should close it.

## Why it is worth real credits

The submission's Kiro write-up asks, in Devpost's own words, *"did PBT catch any issues you might
have missed with unit tests? What kind of requirements did you enable PBT for?"* — see
`docs/kiro-writeup.md`. There is a `TO FILL` block waiting for the answer. A negative answer
("every property held first time") is a perfectly good answer, but it has to be a real one.

The engine is unusually good PBT material: `runScenario` is a pure function from an authored
`Scenario` to a `RunResult`, with no clock, no IO and no randomness. A generator plus six
invariants is most of a day's value for very little code.

## The properties, in the spec's own words

From `design.md` lines 215–217 and the validation plan's invariant table:

1. **Single custody** — at all times each available prop has exactly one `(zone, holder)`;
   `transfer` moves custody without duplicating it.
2. **Terminal consumption** — once `consumed`, an instance never transitions again in the same run;
   `replenish` only takes `absent → available` and never revives a consumed id.
3. **New-instance replenishment** — replenishment only introduces a predeclared absent instance.
4. **Deterministic ordering** — identical input yields an identical `RunResult` across repeated
   runs.
5. **Immutable rejection** — a rejected action does not mutate state; the engine never mutates or
   freezes caller-owned input.
6. **Causal ordering** — a cause is always an **earlier** successful action on the **same**
   instance, or the clearly identified initial state. Never a later action, never another prop,
   never a rejected one.
7. **Own-key-safe dictionaries** — no inherited-property lookups on id-keyed maps.

## What to do

- Add `fast-check` as a dev dependency. Check its advisory status before you commit it; **K9**
  exists because this project already carries dev-only advisories, and adding a new one silently
  would be a poor trade.
- Write a `Scenario` generator — props, zones, holders, cues, ordered actions over the six action
  kinds. The useful shape is a generator of *valid-by-construction* ids and a free choice of
  action kinds and sources, so most generated scenarios are structurally parseable but
  semantically interesting, including rejections.
- One file per property under `tests/pbt/`, or one file with one `test` per property. Either is
  fine; keep each property's failure message able to name the counterexample.
- **Record the seed.** A counterexample nobody can reproduce is not evidence. fast-check prints a
  seed and path on failure; put the reproducing seed in the test as a comment when you fix
  something it found.

## The honest-reporting part, which matters more than the code

Write in `KIRO_SESSION_EVIDENCE.md`, as plain fact:

- which properties you enabled, and for which requirements;
- whether any property **failed**, and if so the minimized counterexample verbatim and what it
  revealed;
- if every property held first time, **say that**. Do not dress up a clean result as a discovery,
  and do not invent a bug to have a story. A judge asking "did PBT catch anything?" is as well
  served by "no, and here are the seven invariants it now guards" as by a dramatic find.

Then fill the matching `TO FILL` block in `docs/kiro-writeup.md` while it is fresh.

## Acceptance

- `tests/pbt/` exists, covering the seven properties above.
- `npm run check` passes, with the real test count reported. It is **235** before this task.
- Each property either holds, or reports a reproducible counterexample with its seed.
- Determinism holds across repeated runs; no test mutates or freezes the engine's input.
- If a property found a genuine engine defect: fix the engine, do not weaken the property. A
  property narrowed until it passes is worse than no property at all.
- `npm run test:e2e` unchanged — this task adds no UI.

## Must not change

Engine behaviour, unless a property proves it wrong — in which case that is the headline of the
session, and it belongs in `KIRO_SESSION_EVIDENCE.md` in full. Do not touch `tests/e2e/`
(reviewer-owned), and do not alter the existing 235 tests to accommodate a generator.

## Record afterwards

Date, CLI version, model and mode, `/usage` before and after, which files Kiro wrote, what failed
on the way, and the final command results. The failures are the convincing part.
