# K5 — the guided fix

**Goal:** from a finding, offer the one edit that would resolve it, apply it on request, and replay
so the verdict visibly changes.

This is the strongest moment in the demo: a contradiction, its cause, a fix, and a clean re-run.

## Scope it narrowly

Do **not** build a general repair engine. Offer a suggestion only for the cases where the missing
edit is unambiguous:

| Finding | The one unambiguous fix |
|---|---|
| `source-mismatch` where the plan leaves the instance with a different holder in the same zone | insert a `transfer` from the planned holder to the required holder, in the cue before this one |
| `source-mismatch` where the plan leaves it in a different zone, no holder either side | insert a `place` into the required zone |
| reuse of a consumed instance | no automatic fix — say that a used-up instance needs a different physical instance, and name the `replenish` step the user would add |

Anything else: say there is no unambiguous fix, rather than guessing. A wrong suggestion in a
planning tool is worse than none, because the user believes it.

## Paste this into Kiro

```text
Add a guided fix to Ghostlight, narrowly.

When a finding is a source mismatch whose only difference is the holder, and the
required and planned zones are the same, offer to insert a transfer action from
the planned holder to the required holder, placed immediately before the failing
action. When the only difference is the zone and neither side has a holder, offer
to insert a place action into the required zone instead.

The offer must say in words exactly what it will insert and where, before the
user accepts: which cue, which position in that cue, which instance by id, and
the source and destination. Accepting applies the edit through the existing edit
layer in src/domain/edit.ts, so the scene stays valid and the change is
undoable the same way any other edit is. The replay then re-runs and the finding
disappears on its own, because the plan changed -- never by suppressing it.

For any other finding, including reuse of a consumed instance, say there is no
unambiguous fix and name the step the user would have to add themselves. Do not
guess.

Do not make the suggested edit automatically, do not change the authored required
source to match the model, and do not alter the engine's rules. The point of this
tool is that requirements are independent of the model; a fix that edited the
requirement to silence a finding would destroy that.

Add tests covering: the holder-only mismatch suggestion, the zone-only
suggestion, a finding with no suggestion, and that accepting a suggestion
produces a scene that replays clean. Then run npm run lint, npm run typecheck,
npm test and npm run build and report the real results.
```

## Acceptance

- On `Missing Handoff — Wrong Holder`, the finding offers to insert the missing transfer in cue 1,
  states that in words, and accepting makes the scene replay with no findings.
- On `Consumed Reuse — Terminal State`, no automatic fix is offered; the text names the replenish
  step instead.
- No path changes `requiredSource` to match the modelled state.

## Must not change

The engine's rules, the independence of authored requirements from modelled state, or the meaning of
any finding code.
