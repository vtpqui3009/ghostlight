# K10 — a haunting interface

**Goal:** make the stage view's ghost-versus-solid idea actually render, and make the visual
language carry the app's meaning instead of decorating it.

## Why this is the category criterion, not polish

Ghostlight is entered in **Costume Contest**, whose published wording is:

> "Build any app but show us a **haunting user interface that's polished and unforgettable. Bring
> in spooky design elements that enhance your app's function.**"

— `docs/KIROWEEN_REQUIREMENTS.md` lines 38–39. "Enhance your app's function" is the whole brief:
the ghost is not a mascot, it is *where the prop was supposed to be*. Design is 20% of judging and
this is the one criterion the category names for itself.

## Measured evidence — the ghost does not currently render

Verified on 2026-11-10 by reading `src/styles.css` and by reading computed styles out of a real
Chromium page.

`src/ui/StageView.tsx` line 222 renders:

```jsx
<div key={`${p.propId}-${idx}`} className={`prop-glyph ${p.type}`}>
```

and `p.type` (line 50) is one of **`required | planned | match | mismatch | other`**.

`src/styles.css` defines exactly these glyph rules: `.prop-glyph`, `.prop-glyph.ghost`,
`.prop-glyph.solid`, `.prop-glyph.match`, `.prop-glyph.mismatch`.

So:

| Rendered class | Rule that matches | What is actually painted |
|---|---|---|
| `prop-glyph match` | `.prop-glyph.match` | green fill, white text |
| `prop-glyph mismatch` | `.prop-glyph.mismatch` | red fill, white text |
| `prop-glyph required` | none | **plain white box, grey border** |
| `prop-glyph planned` | none | **plain white box, grey border** |
| `prop-glyph other` | none | **plain white box, grey border** |
| — | `.prop-glyph.ghost` | **nothing — dead CSS** |
| — | `.prop-glyph.solid` | **nothing — dead CSS** |

Confirmed in the browser: a `prop-glyph planned` element computes to
`background-color: rgb(255, 255, 255)`.

**The dashed, transparent "ghost" and the solid plum "present" treatments exist in the stylesheet
and are applied to nothing.** The distinction survives only in the word labels — `REQUIRED:`,
`BEFORE:`, `MATCH:`, `MISMATCH:` — which is why no test caught it: the information is there, the
visual language is not. Several documents in this repository say "ghost versus solid already
exists". That is true of the CSS and false of the screen.

## A second thing that reads as wrong

`.action-item.selected` (around line 342) paints the selected timeline row with `--mint`, a success
green, **whatever the step's verdict is**. Select the failing step — which is exactly what the demo
script does — and a rejected action sits on a green background with only a small dot disagreeing.

It is also a measured accessibility failure in that state: 1 contrast node in the light scheme and
6 in the dark, recorded in `tests/e2e/axe-baseline.json` under `stage-view-selected` and
`stage-view-selected-dark`, and owned by the reopened part of
[`K2.md`](K2.md). **If you do K10 before that, fix it here and say so in the session notes** — the
two overlap and the token pairs have to be measured either way.

## What to do

1. **Wire the ghost up.** Either rename the CSS to the types the component emits, or map the types
   to the existing names. Renaming the CSS is the smaller change and keeps `StageView.tsx`'s
   vocabulary, which the labels already use.
   - `required` → the ghost: dashed outline, transparent fill, the prop's silhouette *where it was
     supposed to be*.
   - `planned` → the solid: the prop where the plan actually puts it.
   - `match` / `mismatch` → keep the verdict colours; they work.
   - `other` → quiet. It is context, not the subject.
2. **Make the pair legible as a pair.** The moment worth designing is a ghost and a solid in
   *different zones* with a line, an arrow or a gap between them, so the mismatch is visible before
   anyone reads a word. That is the "spooky element that enhances function".
3. **Deepen the palette.** The parchment-and-plum scheme is muted to the point of being
   unmemorable. Push contrast and atmosphere — stage lighting, a gel wash, deep shadow — without
   reaching for the clichés.

## Hard constraints — the research plan rules these out

- **No jump scares.** No sudden motion, no audio, nothing that fires without the user acting.
- **No hidden controls.** Atmosphere never costs discoverability; Design is also judged on
  "intuitive".
- **Respect `prefers-reduced-motion`.** `src/styles.css` line 107 already has the block. Any
  animation you add must have an equivalent static state there, and the meaning must survive with
  all motion off.
- **Both colour schemes.** The dark scheme is a first-class path, not an afterthought — it is
  scanned independently now, and the last thing that skipped it shipped 6 contrast failures.
- **Never express meaning by colour alone.** The word labels stay. A colour-blind judge must read
  the same verdict.

## Acceptance

- Every `p.type` the component can emit has a rule that is actually applied; no glyph falls back to
  an unstyled white box, and no dead `.ghost` / `.solid` rules are left behind.
- The ghost and the solid are distinguishable **with colour removed** and **with motion disabled**.
- `npm run build && npm run test:e2e -- --strict` passes — **0 violations on all nine screens**,
  both schemes, including the selected-row scans. Then re-record the baseline and confirm a plain
  `npm run test:e2e` is green.
- No 390 px horizontal overflow on any view: the responsive specs still pass.
- `npm run check` green at **235 tests or more**.
- A selected rejected row no longer reads as a passing row.

## Must not change

The word labels, the honesty subtitle on the first screen, or anything under `tests/e2e/`
(reviewer-owned). Do not move meaning out of text and into decoration — the whole app's claim is
that it tells you *why*.
