# K6 — reports: CSV export

**Goal:** let a stage manager take the three reports into a spreadsheet.

**Surface:** Kiro CLI.

## Status of this item

K6 originally had two halves. **The responsive half is done**: on 2026-11-10 the reviewer wrapped
each report table in a focusable, labelled `.table-scroll` region, the 73 px overflow at 390 px is
gone and `tests/e2e/known-failures.json` is empty (see `ops/RUN_LOG.md`, run 5). **Only CSV export is
left, and it is Kiro's.** Do not redo the overflow work.

## What already exists

`src/ui/Reports.tsx` renders three `table.report-table` elements — preset, runner, reset — each in a
`.table-scroll` region, plus a button calling `window.print()`. `src/styles.css` has an
`@media print` block. **CSV export does not exist anywhere in `src/`.**

## Paste this into Kiro

```text
Add CSV export to Ghostlight's reports in src/ui/Reports.tsx. The responsive
layout of the report tables is already done -- do not change it.

- One CSV per report (preset, runner, reset), or one file with a "report" column --
  your choice, but say which in the UI and keep the choice obvious to a keyboard
  and screen-reader user (real buttons with accessible names, visible focus).
- Every row carries the physical instance id, not only the display name, because two
  identical props are told apart by id.
- Keep the same rows in the same order as the on-screen report and the printed
  sheet; ordering is part of what makes the sheet trustworthy.
- Quote any field containing a comma, a double quote or a newline, and double any
  embedded double quote.
- Guard against spreadsheet formula injection: a field that begins with =, +, - or
  @ (after any leading whitespace) must not be executed when opened in a
  spreadsheet. Neutralise it in a way that keeps the visible text readable and say
  how.
- The export is a browser file download built from data already in memory. Nothing
  is uploaded anywhere, and no network call is added.
- Keep the planned-state honesty wording on anything exported: the file is a plan,
  not live tracking.

Put the CSV building in a small pure function so it can be tested without a DOM.
Add tests for: quoting a comma, quoting an embedded double quote, a newline inside
a field, a field starting with =, a field starting with +, - and @, a Unicode label,
and an empty report. Do not change what the reports contain.

Then run npm run lint, npm run typecheck, npm test and npm run build and report the
real results, including any failure.
```

## Acceptance

- A CSV can be downloaded for each report, with the physical instance id in every row.
- Quoting is correct and a leading `=`, `+`, `-` or `@` cannot execute as a formula; there are tests
  for each case listed above.
- Row content and order match the on-screen and printed report.
- `npm run check` green with the real test count; `npm run test:e2e -- --strict` still green and
  the axe baseline still empty (new buttons need accessible names).
- No new network request.

## Must not change

What the reports say, their row order, the print stylesheet's behaviour, the `.table-scroll`
responsive handling, or `src/domain/**`.
